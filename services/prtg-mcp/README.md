# PRTG MCP

`flowoox-mcp-prtg` exposes a product-neutral, bounded **read-only** MCP surface for Paessler PRTG monitoring diagnostics. It follows the shared `mcp-common` contracts for query budgets, server-load protection, MCP transport security, correlation IDs and structured audit events.

The initial contract intentionally uses the documented PRTG HTTP API (v1) rather than making arbitrary API calls. PRTG API v2 can be added behind a separately versioned adapter when a deployment requires it; experimental endpoints are not used by this contract.

## Security model

The service registers observe tools only. There is no generic URL, method, table-column, filter, script, object-manipulation or write passthrough. `PRTG_BACKEND_READ_ONLY=true` is a fail-closed deployment assertion and must only be set when the configured API key or authorization proxy has been provisioned for read access. Prefer a dedicated PRTG API key with the lowest supported read-only access level rather than reusing an administrative credential.

Authentication is sent only as `Authorization: Bearer <api-key>`. The service never places the API key in the query string and never returns it in MCP output or audit metadata. Redirects are rejected. HTTPS is required unless `PRTG_ALLOW_INSECURE_HTTP=true` is deliberately set for an isolated trusted environment. TLS verification remains enabled by default.

A Docker socket-style "read-only mount" problem does not apply here, but the same architecture rule does: the backend authorization boundary must be read-only, not just the MCP tool names. If the upstream identity cannot be asserted as read-only, leave `PRTG_BACKEND_READ_ONLY=false` and startup fails closed.

## Observe tools

The service exposes fixed tools for overall health status and health data, bounded device and sensor inventory, current alarm sensors, exact-sensor channel inventory, bounded recent messages, exact-sensor historic data and an aggregate diagnostic bundle. Devices and sensors include probe/group context in the normalized result, so an agent can correlate hierarchy without using undocumented probe/group table calls.

All list tools use bounded page sizes and opaque-to-the-agent decimal cursors generated by the service. Sampling is applied only after raw response cost is charged to the shared query budget. The diagnostic bundle asks for aggregate health and alarm/inventory pages first; it does not fan out to every sensor.

## Historic data load protection

PRTG documents a maximum of five historic-data API requests per minute. The adapter therefore serializes historic requests with a 12-second start interval independently of the normal connector rate limit. It also requires an exact sensor ID, a start and end timestamp in `yyyy-mm-dd-hh-mm-ss`, a fixed averaging value, a deployment-controlled maximum time window and the shared response-byte/time budget.

`refreshnow` is deliberately not exposed for `/api/health.json`, because it can force PRTG to refresh health data. Historic export is never unbounded: raw/sub-hour requests are rejected above PRTG's 40-day limit, all requests are rejected above 500 days, and the stricter `PRTG_HISTORIC_MAX_WINDOW_HOURS` deployment limit defaults to 24 hours.

## Configuration

Copy `.env.example` into deployment-owned secret/config management. Do not commit a real PRTG URL, key, topology or organization policy to this repository. The minimum backend settings are:

```text
PRTG_BASE_URL=https://prtg.example.invalid
PRTG_API_KEY=<secret>
PRTG_BACKEND_READ_ONLY=true
```

The MCP HTTP trust-boundary settings are the same as the other infrastructure MCPs. For externally reachable MCP endpoints, configure the shared issuer/public URL/host/origin controls instead of relaxing them in this service.

## API compatibility

The adapter is limited to documented GET endpoints and parameters:

- `/api/healthstatus.json`
- `/api/health.json?maxage=...` (never `refreshnow`)
- `/api/table.json` with fixed `devices`, `sensors`, `channels` and `messages` content/columns
- `/api/historicdata.json` for an exact sensor and bounded time range

The active-alarm query uses PRTG's documented Warning, Down, Unusual, Down Acknowledged and Down Partial status IDs. Message windows are restricted to `today`, `yesterday` or `7days`.

## Development

From the repository root, install through the pinned constraint graph and run the same gates as CI:

```bash
python -m pip install --constraint constraints/python312.lock ./packages/mcp-common
python -m pip install --constraint constraints/python312.lock -e './services/prtg-mcp[dev]'
python scripts/check_python_lock.py flowoox-mcp-common flowoox-mcp-prtg pytest pytest-asyncio ruff
ruff check packages/mcp-common/src services/prtg-mcp/src services/prtg-mcp/tests
pytest -q services/prtg-mcp/tests
python -m compileall -q packages/mcp-common/src services/prtg-mcp/src
```

A future write layer, if implemented, must use a separate least-privilege write identity and the repository's `plan -> approval -> change -> verify` contracts with idempotency, pre-state capture, rollback declaration where possible, and independent read-back verification. It must not broaden this read-only adapter.
